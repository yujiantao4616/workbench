# Codex Workbench 工作流改进计划

日期：2026-10-19  
状态：基于现有源码和本次访谈的实施计划；尚未实现、未启动定时任务、未连接或修改外部系统。

## 1. 改造目标与已确认约定

将现有需求整理与执行工作台，升级为围绕需求和修复批次工作的本地托管工具。保留现有需求澄清、项目管理、快速修改、记忆和周报能力。

| 环节 | 已确认的工作方式 |
| --- | --- |
| 需求入口 | 用户只提供 TAPD Story 链接；系统获取关联飞书文档、接口资料和截图。无法判断代码项目时由用户指定；一个 Story 可以对应多个项目。 |
| 需求确认 | 保留先读代码、固定提示词扩写、用户审阅和补充提问的流程。用户确认需求后进入开发。 |
| 完成目标与用例 | AI 自动生成并执行，不增加用户确认测试用例的环节；保存用例和执行证据，支持事后查看。 |
| 测试环境 | 本地服务、公司内网测试环境、鸿蒙模拟器及真机。自动完成普通登录，复用登录态；优先使用自己创建的测试数据。 |
| Bug 来源 | 每小时同步，自动处理分配给用户且处于项目所定义“待处理／重新打开”状态的 Bug。状态名称和内部值按 TAPD 项目映射。 |
| 执行粒度 | 同项目 Bug 汇成批次，统一分析关联、统一修改，逐条验证及关联回归，一起提交。执行中新到的 Bug 留到下一批。 |
| 分支与目录 | 用户提前建立并指定开发分支；使用现有目录，同项目串行。保留用户偶尔手改的内容。需求和 Bug 默认前后衔接，不做抢占调度。 |
| Git 权限 | 可以在指定分支提交并推送；标签权限仅限 test 标签。打包、TKD 和发布平台由用户操作。 |
| 自动修复上限 | 每个 Bug 或不可拆分的关联组最多 3 轮“修复＋自测”；受阻则留存现场。定时轮询或重启不能重置轮数。 |
| 部分成功 | 可独立交付的先提交；相互依赖的改动一起等待，不提交半成品。 |
| 发布衔接 | 用户点击“该批次已发布”，按实际发布的项目及提交范围回写 TAPD 状态；代码修完不等于已经提测。 |
| 通知 | 飞书应用机器人只私聊用户本人。按半天或配置的时间窗口汇总，不逐条通知 Bug，不自动通知测试同事。 |
| 后台运行 | 关闭窗口后保持后台工作；休眠、断网后恢复补查。退出应用或关机期间不执行，不假设全天在线。 |
| 留痕 | 材料、目标、用例、实际执行、修改、提交、发布确认、状态回写和通知均可追溯。 |

## 2. 现有功能与需要补齐的部分

以下依据当前源码，不能将旧 README 中的规划当成已实现能力。

| 模块／代码 | 可复用能力 | 主要缺口 |
| --- | --- | --- |
| `services/tapd.ts`、`TapdModule.tsx` | 获取当前用户参与的项目及 Bug／Task／Story；打开 TAPD 页面自动同步一次；手动同步、表格导入 | 没有主进程小时调度；列表请求固定 limit=200、无分页；没有按 Story 链接完整取材；自动执行资格尚未建立。 |
| `App.tsx: sendTapdBatchToPrompt` | 多个 TAPD 记录合成一个 WorkItem，保留 externalSources，进入需求流程 | 当前是用户选择项目和记录后触发；需要搬到主进程，由可恢复的批次服务调用。 |
| Prompt、`promptPresets.ts`、`promptBuilder.ts` | 读项目上下文、扩写、追问、生成目标／范围／约束／验收标准 | 缺少材料版本、结构化完成目标、测试用例与验收项的关联。保留现有提示词和用户编辑值。 |
| TaskGroup、Kanban、Issues | 一份需求分发多个项目、任务状态、快速修改 | 需要把跨项目需求组与同项目 Bug 批次分开建模；补充分支、环境、发布范围。 |
| `codex.ts`、`runManager.ts` | CLI 执行、日志、反馈续改、取消、总结、Git 快照与 Undo | 每次启动新 exec；未持久化真实会话 ID；没有结构化测试判定、自动修复循环、恢复检查点。 |
| `store.ts` | 集中存储、临时文件替换写入、重启时标记中断、任务历史 | JSON 全量读改写、日志只留最近 80,000 字符；仅串行写文件不能保证多个读改写事务不互相覆盖。 |
| `git.ts` | 分支查询／切换、提交、推送、前后树差异与逆向补丁 | 当前 commit 使用 git add --all，push 依赖当前 upstream；需要指定分支校验和按本批改动提交。现有 tree 快照不是隔离 worktree。 |
| `App.tsx: completeTask` | 完成任务后回写关联 Bug 的“我已完成” | 必须将“代码完成”与“发布后提测”分开，移除自动化路径中的提前回写。 |
| `main.ts`、系统通知 | Electron 主进程、macOS 关闭窗口不直接退出、执行结束系统通知 | 没有托盘调度中心、持久化计划和飞书私聊汇总；自动批次不再逐条弹完成通知。 |
| Memory、WeeklyReport | 多层记忆、任务结论归档、周报 | 复用批次及验证记录生成总结；详细日志进入证据档案，不全部灌入长期记忆。 |

同步可靠性还要修正：`replaceTapdMyWork` 会先移除旧 API 来源记录，再替换为本次结果；当前拉取可部分失败或因时间预算跳过请求。自动托管后必须按项目、类型、分页记录完整性，失败不能当成记录已消失。

## 3. 两条目标流程

### 需求开发

```text
粘贴 Story 链接
→ 自动取材，保存来源和版本
→ 识别涉及项目；不明确时由用户指定
→ 读代码、扩写、用户审阅、补充提问
→ 固化本轮需求目标
→ AI 生成用例、开发、自测和修正
→ 提交推送，交给用户复测与发布
→ 用户按项目确认发布范围
→ TAPD 状态回写、汇总通知
```

跨项目需求沿用 TaskGroup，每个项目有独立分支、运行、测试和发布状态；只有必要的共享接口依赖才排先后顺序，不强制所有项目一起完成。

### Bug 自动托管

```text
每小时同步
→ 校验处理人、状态、项目映射及重复处理记录
→ 按项目＋指定分支形成固定批次
→ 复现、识别关联、制定用例
→ 修改 → 自测 → 必要时继续修复（最多 3 轮）
→ 选择可独立交付的改动，回归验证实际交付版本
→ 提交并推送
→ 待用户发布
→ 用户确认已发布 → 回写 TAPD
→ 按时间窗口私聊汇总给用户
```

没有新记录和状态变化时静默。映射不清、资料不足、后端不可用、设备离线等情况标记受阻，不进入无限修复。基础设施重试与代码修复轮次分别记录，并设置有界超时。

## 4. 必须落在代码里的执行规则

### 4.1 批次和状态

批次建议状态：待处理、分析中、修复中、自测中、待提交、推送失败、待发布、部分待发布、受阻、已交付。另行记录每个 Bug 的结果，不用一个批次状态替代全部成员状态。

发布记录独立保存“用户确认发布、TAPD 回写、通知发送”三种状态。已发布但回写失败可以重试回写；已推送但应用重启不能重跑修复；远程响应丢失时先核对实际状态。

代码完成和发布后提测均不自动代表测试验收、关闭 Bug。测试再次打开 Bug 时建立新一轮关联记录，保留上一轮复现、提交和发布历史。

### 4.2 去重与恢复

- 记录标识使用 TAPD workspace＋类型＋记录 ID，不能仅按标题或 defectId 去重。
- 同一 Bug 同一处理周期只允许一个活动批次。记录内容版本和重新打开周期；系统自己的状态回写不能被识别成新 Bug。
- 执行前再次核对远端处理人及状态，已转交或关闭的记录不继续自动执行。
- 同步周期、批次成员、会话 ID、轮数、提交 SHA、推送及回写意图持久化；重启先核实状态再恢复。
- 开始批次后冻结成员。新增 Bug 排下一批；执行中原 Bug 发生业务内容变更则记录差异、重新分析，不能用旧验收结果覆盖新要求。
- 受阻项不会因每小时同步重新获取 3 轮预算。材料补齐、环境恢复或用户重试可开启有记录的新尝试。
- Story 与 Bug 默认串行。若意外同时到达，只入队，不中断正在执行的工作。

### 4.3 Git 与部分交付

- 按实际仓库路径加执行锁，在启动、提交、推送前核对用户指定分支和远程目标；分支变动、远端分叉等情况保留现场并受阻，不自动 force push。
- 记录开始时的 HEAD、暂存区、未提交及未跟踪文件。对用户已有修改按文件／差异块保护，不能直接沿用 git add --all。
- 为关联 Bug 组建立改动归属及检查点。批次可包含多个独立组，但同一项目串行执行。
- “4 个成功、1 个失败”时，先构造实际可交付的变更集合，再针对该集合回归。失败组若与成功组共享不可拆分的代码，就一起等待。
- 不以干净工作区为由删除用户文件。恢复检查点、撤回失败组时先核对后续变化；无法安全区分则受阻。
- 保留现有 Undo 作未提交改动辅助；已经推送的改动需通过有记录的新修复或 revert 提交处理，不把逆向补丁等同于远端回滚。
- test 标签采用项目明确配置的命名规则和目标提交，不覆盖已有标签、不创建生产标签。默认不在每批提交后自动打 tag；若 test tag 会触发 TKD 发布，仍放在用户主导的发布环节，避免越过“发布由用户负责”的边界。

### 4.4 自测必须有执行证据

先形成需求／Bug → 完成目标 → 测试用例映射，再开发执行。代码变化后可以补充用例，但不得为通过测试而静默降低已确认需求的预期。

每条用例至少保存：对应目标、前置条件、环境、操作步骤、预期、实际结果、证据路径、运行时间、代码版本。状态为通过、失败、受阻、未执行；没有证据不能标成通过。

| 测试层级 | 第一版行为 |
| --- | --- |
| 静态／构建 | 使用项目现有 typecheck、lint、单元测试和构建命令；明确实际执行了哪些命令。 |
| Web 页面 | 操作本地前端，连接配置的内网测试后端；覆盖需求主流程、相关异常及受影响回归，保存截图、断言与必要日志。 |
| 接口 | 根据接口资料核验关键请求、字段、错误处理；只依赖 Mock 的结果单独标记。 |
| 鸿蒙 | 按配置的模拟器／真机执行，记录设备、系统、包和代码版本。模拟器通过不代表真机通过。 |

未发布前不能用仍在运行旧版本的共享测试站证明新代码通过。每次测试绑定当前启动服务或安装包；报告明确“本地新代码＋测试后端”与“已发布环境”的区别。

登录凭据使用本机凭据存储引用，复用专用测试会话；自动创建测试数据并记录其 ID，优先只修改／清理本次创建的数据。验证码或设备授权等无法自动完成的步骤标记受阻。

## 5. 界面改造：复用现有模块，减少跳转

| 现有入口 | 改造后职责 |
| --- | --- |
| Issues／需求 | 增加 TAPD 链接入口、材料完整性、涉及项目、现有澄清对话。 |
| TAPD | 保留记录列表和手动同步；增加最近同步、下次同步、自动处理资格、关联批次、受阻原因。 |
| Kanban | 展示需求、执行批次及待发布队列；区分代码完成与发布后提测。 |
| Executor | 改成任务／批次详情：目标、材料、关联 Bug、过程、用例与证据、提交和发布记录在同页查看。 |
| Settings | 每项目配置目录、分支、TAPD 映射、测试环境／命令／账号引用、设备、托管开关和汇总时间。 |
| Memory／周报 | 延用现有入口，补充批次来源链接及验证状态。 |
| 托盘 | 显示运行状态、待发布／受阻数量；支持打开窗口、暂停新任务、停止当前运行和明确退出。 |

用户日常主要操作是：粘贴 Story、确认需求及项目、查看结果、发布后确认批次。测试用例审核、正常 Bug 修复和提交推送不新增逐次确认。

## 6. 数据与服务设计

保留 AppStore 对外抽象。建议将关系数据和队列迁到 SQLite，以事务保证批次认领、状态推进及外部操作记录的一致性；截图、附件和运行日志存放文件，界面只传增量和摘要。

| 新增记录 | 核心作用 |
| --- | --- |
| ProjectAutomationProfile | 项目／TAPD 映射、指定分支、远程、测试环境、凭据引用、设备和托管设置。 |
| RequirementSnapshot / MaterialSnapshot | Story 及关联材料的原始来源、时间／版本、提取内容、完整性和访问失败原因。 |
| ExecutionBatch / BatchIssue | 固定批次成员、关联组、处理周期、目标分支、逐条结果、轮数和依赖。 |
| AcceptanceCriterion / TestCase / TestRun | 目标、用例版本、实际执行与证据。 |
| ChangeSet / CommitRecord | 本批文件／差异块、基线、提交 SHA、包含的 Bug、推送结果。 |
| ReleaseRecord | 用户确认的项目、环境、提交范围、发布时间及对应交付项。 |
| SyncCheckpoint / ScheduledJob | 同步完整性、运行锁、下次运行、恢复检查点。 |
| Outbox / AuditEvent | TAPD 回写、飞书消息等外部操作的意图、尝试、结果和重试记录。 |

建议新增 `batchManager`、`scheduler`、`testRunner`、`materialCollector`、`releaseService`、`notificationService`、`credentialStore`；扩展现有 `tapd`、`git`、`codex` 和 `runManager`，由主进程协调，不依赖 React 页面是否打开。

迁移前备份原 data.json 和附件，保留旧记录 ID、关联、用户提示词和旧目录标识。迁移可重复验证、失败可回退。原来已被截断的日志无法补回；新运行才开始完整留痕。原始执行记录可脱敏落盘，不能把密码／令牌写进报告或归档。保存策略需显式配置，首版不自动清除历史证据。

## 7. 实施顺序与验收

### 阶段 0：可恢复执行与记录基础

交付：数据迁移、批次／测试／发布模型、完整日志、事务和仓库锁；分支及提交范围校验；把业务状态推进从 App.tsx 移到主进程。整理 Node／Electron 兼容环境，补上独立于 UI 的服务测试入口。

验收：旧项目、任务和提示词可读取；中断恢复不重复提交；并发状态写入不丢记录；用户原有改动不被覆盖或误提交。当前目录未检测到 .git，正式源码开发前先确认版本管理或建立可恢复基线。

### 阶段 1：单项目批量修复与 Web 自测

交付：先复用现有 TAPD 列表和批量入口，接通真实 Codex 会话、结构化运行状态、动态模型能力；自动生成用例、执行页面测试、最多 3 轮修复、部分成功提交和指定分支推送。此阶段可手动选择一批记录验收，随后由阶段 2 定时触发同一套流程。

验收：在用户指定的试点项目与分支，用一批包含独立及关联问题的样例完成复现、修复、测试和提交；可证明成功项不包含失败项的残留改动。构建通过不替代页面测试，模型声明完成不替代实际证据。

### 阶段 2：小时托管、发布确认与飞书汇总

交付：TAPD 分页和可靠增量合并、项目／状态映射、后台小时任务、去重与重新打开周期、恢复补查；待发布批次页；发布后 TAPD 回写；飞书应用机器人向用户本人定时私聊。建立具体窗口配置（Asia/Shanghai），半天为初始粒度，具体发送时刻设置时再定。

验收：关窗口仍运行；连续轮询不重复修；跨 200 条列表不漏项；部分同步失败不丢历史；受阻项不无限重试；发布前不标成已提测；重复点击发布不重复回写；通知失败只重试通知。消息包含已修复待发布、已发布／回写结果和受阻项，无变化时静默。

阶段 0～2 构成第一个可用版本：优先解决人工刷新 TAPD、逐个交给 AI、重复自测和整理通知的问题。

### 阶段 3：Story 链接自动取材与多项目开发

交付：从 Story 链接获取完整详情、排期和材料；飞书文档／图片读取；Apifox 项目接口资料读取；材料版本和缺失提示；复用现有澄清流程、TaskGroup 和阶段 1 的测试执行器；各项目独立交付和发布确认。

验收：一个实际 Story 链接可以进入完整需求澄清；材料取不到会明确显示，必要材料缺失时不静默进入开发；一个 Story 的两个项目分别展示目标、测试和发布结果；资料更新不会悄悄改变已确认目标。

### 阶段 4：鸿蒙模拟器与真机测试

交付：在相同用例／证据模型下接入鸿蒙测试执行器，支持测试构建、安装、启动、登录、操作、截图和日志；配置设备选择、占用锁、签名和工具链检测。应用测试安装不代替用户负责的对外打包发布。

验收：选一个鸿蒙项目，分别在模拟器及已授权真机完成典型流程；掉线、安装失败和包版本不匹配明确受阻；报告能追到具体设备和安装包，不能把 Web 或模拟器证据标成真机通过。

### 阶段 5：依据实际结果收敛

统计人工介入次数、自动复现／修复率、首轮通过率、3 轮受阻率、重开率、单批耗时、用量、误报漏报及通知重复。通过时间窗回顾失败案例，调整用例、提示词和批次策略；运行时长与用量预算可配置，耗尽后保留状态，不无限运行。

验收：能按项目和时间范围查阅“自动做了什么、哪些经过真实验证、哪些最终重开”；是否扩大托管项目依据实际结果决定，不先承诺全自动成功率。

## 8. 实施时的关键回归场景

1. 多页 TAPD 数据、一次部分请求失败、同一 workspace 中 Bug 重新打开，以及不同 workspace 相同数字 ID。
2. 批次创建／提交／推送／TAPD 回写／通知发送前后分别模拟退出，确认恢复不会重复业务动作。
3. 用户已有暂存／未暂存修改、运行中改动一两行、目标分支变化、远端 push 被拒绝。
4. 同批 5 个 Bug，4 个通过、1 个失败；再覆盖失败项与成功项共享文件及共享逻辑的情况。
5. 测试通过、断言失败、未执行、登录失败、后端离线、测试站仍是旧代码，必须有不同结果。
6. 未发布、部分项目发布、部分提交发布、重复确认、TAPD 回写失败及飞书发送失败。
7. 关窗口、重启、电脑休眠、网络恢复；累计修复轮次不能重置。
8. 旧数据迁移中断／重试／回退，旧任务仍能浏览和手动执行。

服务层用可控样例验证这些状态转换；实际接通后，再用一个 Web 项目和一个鸿蒙项目验证真实链路。模拟结果与内网实测分别记录。

## 9. 一次性接入条件与范围

这些在对应阶段设置，不再增加每个任务的确认：TAPD 实际权限与状态转换；TAPD 业务项目到一个或多个代码仓库的映射；用户指定分支及 GitLab 访问；本地启动命令与测试环境；测试账号；飞书应用凭据、本人接收标识及文档访问权限；Apifox 项目／文档访问；鸿蒙工具链、签名与设备。

飞书应用机器人私聊需要启用对应能力、发送权限及用户可用范围；文档读取另行确认授权。Apifox 优先使用已授权的项目文档／MCP 或 OpenAPI 原始文档入口；连接信息只需设置一次，不把日常流程退回手工导出。接口支持情况在接入真实账号时验证。

当前聊天具备的浏览器、应用工具和技能不等于独立 Electron 程序已具备同样能力。Web／鸿蒙操作必须真正接入工作台执行环境并完成验证，不能仅靠提示词要求“请自测”。

第一版不做自动生产发布、不代操作 TKD、不扩展为多 AI 并行、不自动私聊测试同事；不用跨项目大规模升级依赖来替代工作流落地。

- [Apifox 官方导出数据文档](https://docs.apifox.com/export-data)：接口可提供 OpenAPI 等结构化资料和原始内容入口；具体私有项目的自动访问方式需实测。

本计划基于源码核对和已确认的工作方式，不代表外部权限、真实浏览器自动测试、鸿蒙自动测试或后台托管已经验证通过。
